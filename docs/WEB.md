# Веб-часть: Django и админка (этап 4)

## Быстрый запуск (разработка, SQLite)

```bash
bash setup.sh                         # миграции, роли и синтетический семестр создаются на шаге 5
source .venv/bin/activate
python manage.py createsuperuser      # почта + пароль; логина-«username» нет
python manage.py runserver            # http://127.0.0.1:8000/admin/
```

## Переменные окружения

| Переменная | По умолчанию | Назначение |
|---|---|---|
| `DJANGO_DEBUG` | `1` | `0` в продакшене |
| `DJANGO_SECRET_KEY` | ключ разработки | **обязателен** при `DJANGO_DEBUG=0` — без него сервис не стартует |
| `DJANGO_ALLOWED_HOSTS` | `localhost,127.0.0.1` | имена сервера через запятую |
| `DB_ENGINE` | `sqlite` | `postgres` в продакшене (PostgreSQL 15+, требование Django 6.1) |
| `DB_NAME` | `schedule` / `data/dev.sqlite3` | имя БД (для SQLite — путь к файлу) |
| `DB_USER`, `DB_PASSWORD`, `DB_HOST`, `DB_PORT` | `schedule`, пусто, `localhost`, `5432` | подключение к PostgreSQL |
| `SCHEDULE_DATA_DIR` | `./data` | каталог для SQLite-файла |
| `EMAIL_HOST`, `EMAIL_PORT` | пусто, `465` | SMTP-сервер для кодов входа. Пусто — письма печатаются в консоль |
| `EMAIL_HOST_USER`, `EMAIL_HOST_PASSWORD` | пусто | ящик и **пароль приложения** (не пароль от ящика) |
| `EMAIL_USE_SSL` / `EMAIL_USE_TLS` | по порту: 465 → SSL, 587 → TLS | обычно задавать не нужно |
| `DEFAULT_FROM_EMAIL` | `EMAIL_HOST_USER` | отправитель, например `Расписание <raspisanie@college.ru>` |

Переменные можно не задавать в системе, а вписать в файл `.env` в корне проекта: скопируйте
`.env.example` в `.env` и заполните. Заданное в системе важнее файла. Файл `.env` в архивы и git не
попадает.

Пример для PostgreSQL:
```bash
export DB_ENGINE=postgres DB_NAME=schedule DB_USER=schedule DB_PASSWORD=*** DB_HOST=127.0.0.1
python manage.py migrate && python manage.py init_roles
```

## Команды manage.py

| Команда | Что делает |
|---|---|
| `create_semester "Осень 2026" 2026-09-01 [--saturday] [--first-week even]` | семестр с сеткой 7 пар и курсами 1–4 (лимиты и сетки смен — значения [уточнить]) |
| `seed_synthetic [--seed N] [--tightness 0.5] [--if-empty]` | синтетический семестр масштаба колледжа |
| `init_roles` | группы «Администратор», «Диспетчер», «Преподаватель» с правами (идемпотентно) |
| `export_problem <семестр> -o problem.json` | задача ядра из БД + быстрые проверки; JSON совместим с `schedule_cli.py` |
| `create_api_token почта [--name …] [--days N]` | выпустить токен API (показывается один раз) |
| `solve_worker [--once] [--poll 3]` | обработчик расчётов: забирает запуски «Построить расписание» из очереди и считает; держать запущенным рядом с сайтом |
| `solve_semester <семестр> --time 120 --variants 3 [--preset Имя] [--reference-variant ID]` | расчёт прямо в этом окне, без очереди; попадает в «Запуски расчёта», варианты сохраняются в БД |
| `draft_from_schedule текущее.xlsx -o output/draft` | черновики справочников и нагрузки из текущего расписания + отчёт о сомнительном |

`<семестр>` — id или точное название.

## Что умеет админка

**Семестр** — даты, чётность первой недели, суббота, правила (окно очно→онлайн, лимиты); сетка
пар и курсы редактируются прямо в карточке. В списке семестров у каждого — ссылки:
«Построить расписание» (фоновый расчёт), «Проверить» (быстрые проверки + полнота данных),
«Нагрузка ⇣/⇡ xlsx», «Справочники ⇣/⇡», «Задача JSON».

**API** (0.9.0) — `/api/v1/`, описание и примеры — [API.md](API.md), интерактивная документация —
`/api/v1/docs`. Токены для программ — раздел «Токены API» или `manage.py create_api_token`. Изменения
через API видны в «Недавних действиях» с именем токена. ИИ-агент диспетчера — [MCP.md](MCP.md).

**Запуски расчёта** (0.8.0) — очередь и история. Кнопка «Построить расписание» создаёт запуск
«в очереди»; обработчик `solve_worker` забирает его, раз в 2 с пишет прогресс (вариант, этап,
оценка штрафа и нижняя граница), журнал и «последний отклик». Страница запуска обновляется сама,
кнопка «Остановить и сохранить найденное» останавливает решатель за секунды, найденные варианты
сохраняются. Одновременно у семестра не больше одного активного запуска (ограничение в БД).
Запуск без отклика дольше 2 минут (обработчик остановили) помечается «не построено». Очередь —
своя таблица, а не Procrastinate из ТЗ: тот требует PostgreSQL, а пилот идёт на SQLite.
Права: «добавлять запуск расчёта» — запускать, «изменять» — останавливать (роль «Диспетчер»).
Ядер решателю — не больше `SOLVER_MAX_WORKERS` (по умолчанию все, кроме одного).

**Курсы и группы** — лимиты в день (каждый можно сделать жёстким), сетка смены курса и
переопределение у группы — таблицей «дни × пары» с выпадающими −2…+2 и цветом.

**Преподаватели и доступность** — сетка −2…+2 на семестр (одна на обе недели), отметка
«заполнено». Пока её заполняет диспетчер; форма для самих преподавателей — этап 7.

**Нагрузка** — таблица с фильтрами (семестр, вид, формат, тип аудитории, курс, блок,
объединение), поиском по дисциплине/преподавателю/группе, правкой числа пар прямо в списке.
Действия: «Копировать выбранные», «Выгрузить в xlsx». Кнопка «Массовое создание» — одна
дисциплина на несколько групп: по элементу на группу, одним потоком или как допустимое
объединение. Закрепления — внутри карточки элемента.

**Особые схемы (0.3.0).** В нагрузке — колонки «недели», «бронь аудитории», «кто ставит»,
фильтры «Кафедра» и «Подсказки» (кандидаты «через неделю», кандидаты на бронь аудитории) и
действия: «Схема „через неделю“», «Забронировать аудиторию преподавателю», «Ставить вручную».
Элементы «вручную» (элективы, кружки) решатель учитывает, только когда закреплены все их пары;
страница «Проверить» показывает, какие из них пока пропускаются.

**Языковой блок курса** — в списке курсов ссылка «Создать блок курса»: все группы курса
распускаются, по подгруппе на каждого выбранного преподавателя, все — в одно время.

**Площадки (0.4.1).** Справочник «Площадки» хранит время закрытия, у аудитории указана её
площадка. Пары, которые заканчиваются позже закрытия, на площадке не ставятся: ни очные, ни
дистант с бронью. Исключение — занятия с флажком «можно закончить раньше», например киноклуб: им
можно 7-ю пару, и в расписании у них пометка «до 21:00». Онлайн-пары из дома ограничение не
затрагивает.

**Вместимость (0.4.1).** В настройках семестра есть флажок «учитывать вместимость аудиторий».
По умолчанию он выключен, потому что посещаемость не 100%. Тогда численность групп не мешает ни
выбору аудитории, ни потокам и объединениям, а решатель лишь старается подбирать аудиторию по
размеру. Если включить флажок, вместимость станет жёстким ограничением.

**Аудитории и оборудование (0.4.0).** Справочник «Оборудование» настраивается (проектор,
компьютеры, RTX, ПО …). В аудитории — её оборудование; у преподавателя — «необходимое оборудование»
(жёстко) и «предпочтительные аудитории» (по возможности); у элемента нагрузки — своё оборудование.
«Занятость аудиторий (не нами)» — сетка с галочками на семестр: в эти пары аудиторию не взять.

**Потоки.** Фильтр «Подсказки → кандидаты на поток» и действия «Поток: разрешить» (решатель объединит,
если выгодно) и «Поток: всегда вместе» (один элемент на все группы).

**Просмотр варианта.** В списке вариантов у каждого — «расписание» (сетка группы / преподавателя /
аудитории, чётная или нечётная неделя), «свободные аудитории» (день, диапазон пар, неделя, мест не меньше,
тип, оборудование) и «часы» (часы к табелю: поток — по каждой группе; есть выгрузка в xlsx).

**Черновик из текущего расписания.** Семестры → «Черновик из текущего расписания»: загрузите файл, в
котором сейчас ведётся расписание, — получите zip с черновиками справочников и нагрузки в наших шаблонах и
отчётом о сомнительных ячейках. В базу ничего не пишется, пока вы не загрузите проверенные черновики.

**Синхронные блоки** — группы, которые «распускаются», и занятия-подгруппы блока с
численностью и уровнем; столбец «пар за цикл» подсвечивает красным разное число пар.

**Пресеты весов** — вес каждого критерия отдельным полем с понятной подписью, цена значений
шкалы, режим (взвешенный / лексикографический). Пресет «по умолчанию» используется
`solve_semester` без `--preset`.

**Варианты** — штраф по критериям, назначения, действия «Утвердить» (с проверкой валидатором;
остальные варианты семестра становятся черновиками) и «Перепроверить валидатором».

## Модель данных: что на семестр, что на организацию

```
организация:  Department, Equipment, Teacher, Discipline, RoomType, Room, WeightPreset, User, AllowedEmail
семестр:      Semester ─┬─ PairTime (сетка пар)
                        ├─ Course ── Group ── Subgroup
                        ├─ TeacherAvailability (сетка −2…+2 преподавателя на семестр)
                        ├─ RoomAvailability (слоты, когда аудитория занята «не нами»)
                        ├─ WorkloadItem ─┬─ teachers / groups / subgroups (M2M)
                        │                ├─ sync_block → SyncBlock (группы M2M)
                        │                ├─ merge_group → MergeGroup
                        │                └─ Pin (закрепления)
                        └─ ScheduleVariant (снимок задачи JSONB) ── ScheduleAssignment
```

Поля «на вырост» под открытые вопросы (docs/OPEN_QUESTIONS.md): `WorkloadItem.week_pattern`
(с 0.3.0 — «обычная» и «через неделю»), `WorkloadItem.alt_room_types` (допустимые замены типа аудитории — пока
не учитываются решателем), число пар хранится у каждого элемента блока, блок не привязан к курсу.
Ответы на вопросы не потребуют миграции данных.

## Пользователи и вход по коду (этап 7, версия 0.6.0)

**Как это выглядит для преподавателя.** Он открывает `/login/` и вводит рабочую почту. На почту
приходит код из 6 цифр, после ввода кода он попадает на страницу «Мои пожелания» (`/me/`). Там:

- сетка пожеланий на семестр по шкале −2…+2;
- его нагрузка;
- его расписание, когда вариант утверждён.

Пароль не нужен. Чужие пожелания и чужое расписание преподаватель не видит.

**Правила кода:**

- код действует 10 минут, на ввод даётся 5 попыток;
- новый код можно запросить не чаще раза в минуту и не больше 5 раз в час;
- в базе хранится только хэш кода;
- на адрес не из белого списка письмо не отправляется, но ответ на странице тот же. Так нельзя
  выяснить, кто есть в списке.

**Что сделать диспетчеру:**

1. Вписать почту в карточки преподавателей. Можно в Excel: «Справочники ⇣», колонка «Почта».
2. В списке преподавателей отметить нужных и выбрать действие «Разрешить вход по почте». Адреса
   попадут в белый список с ролью «Преподаватель».
3. Указать в карточке семестра «срок сдачи доступности». После него страница только для
   просмотра, а пожелания сохраняются как были.
4. Следить за сдачей: ссылка «Пожелания» в строке семестра. Там видно, кто может войти, кто входил
   и кто сдал.

**Роли из белого списка.** «Преподаватель» попадает на свою страницу. «Диспетчер» и
«Администратор» получают доступ в админку (группа и флажок «персонал»), после входа по коду их
переводит в `/admin/`. Учётная запись создаётся при первом входе и привязывается к карточке
преподавателя с той же почтой.

**Почта.** Пока `EMAIL_HOST` не задан, письмо с кодом печатается в окне, где запущен сервер.
Так можно проверить вход без почтового ящика. Реальный ящик подключается в `.env`, проверка
настроек — `python manage.py test_email ваш@адрес`. История отправленных кодов (без самих кодов)
лежит в админке: «Коды входа».

**Чтобы преподаватели могли зайти со своих устройств,** сервис должен быть доступен им по сети.
`runserver` на ноутбуке диспетчера для этого не годится. Для пилота внутри сети колледжа можно
запустить `python manage.py runserver 0.0.0.0:8000` и добавить адрес машины в
`DJANGO_ALLOWED_HOSTS`. Нормальное размещение — сервер с HTTPS и доменом — относится к этапу 8.
