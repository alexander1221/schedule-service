# Архитектура ядра

## Поток данных

```
 справочники + нагрузка + пожелания            (сейчас: generator.py / JSON; этап 4: Django ORM)
                │
                ▼
        domain.Problem  ──────────────► serialization  ──► JSON-снимок (JSONB варианта)
                │
                ▼
        precheck.precheck()  ── ошибки ──► «у Петрова 8 пар и 6 слотов»  (стоп)
                │ ок
                ▼
   ┌──── Solver (протокол, solver/base.py) ────────────────────────────────┐
   │  CpSatSolver                                                          │
   │   ├─ _Builder.build(): единицы, переменные, жёсткие, индикаторы       │
   │   ├─ run(): фаза 0 (любое решение) → оптимизация с полной подсказкой  │
   │   │         (взвешенно или по уровням лексикографии)                  │
   │   ├─ extract() → назначения без аудиторий                             │
   │   ├─ rooms.assign_rooms(): задача о назначениях по слотам             │
   │   ├─ validator.validate()  (защитный контур: 0 жёстких нарушений)     │
   │   └─ повтор для следующего варианта с «отличаться на ≥ K»             │
   │  при INFEASIBLE → diagnose(): ядро противоречий через assumptions     │
   └───────────────────────────────────────────────────────────────────────┘
                │
                ▼
        SolveResult: варианты (Schedule + разбивка штрафа от валидатора) / диагностика
```

## Компоненты

| Модуль | Делает | НЕ делает |
|---|---|---|
| `domain.py` | dataclass'ы, индексы, производные величины (численность, «клетки», доступные слоты) | не знает о БД, решателе, вебе |
| `criteria.py` | список мягких критериев, подписи, веса по умолчанию, пресеты, режимы | ничего не считает |
| `defaults.py` | значения [уточнить]: сетки смен, лимиты курсов | — |
| `precheck.py` | быстрые необходимые условия разрешимости, человеческие сообщения | не доказывает разрешимость |
| `validator.py` | все жёсткие правила и все штрафы «в лоб» по готовому расписанию | **не импортирует решатель** |
| `solver/base.py` | протокол `Solver`, параметры, прогресс, результат | — |
| `solver/cpsat.py` | модель этапа 1, оптимизация, варианты, пересборка, диагностика | не выбирает аудитории |
| `solver/rooms.py` | этап 2: конкретные аудитории | не двигает занятия по слотам |
| `generator.py` | синтетика с посаженным решением | — |
| `cli.py` | командная строка | — |

## Почему такой дизайн

**Единица решателя.** Отдельный элемент, синхронный блок и объединённое занятие — всё это
«нечто, получающее слот целиком». Обобщение убирает три разные ветки кода из ограничений:
преподаватели, клетки групп и аудитории суммируют занятость единиц одинаково.

**Переменные `w[u,s]` и `b[u,s,k]` вместо `x[u,s,k]`.** Еженедельная пара обязана стоять в одном
слоте обе недели — в `x`-формулировке это пришлось бы связывать дополнительными ограничениями.
Мигающая пара занимает только свою неделю, поэтому две мигающие разных занятий могут делить слот.

**«Клетки» студентов.** Подгруппы разных делений (лабы пополам, английский по уровням) пересекаются
по студентам. Конфликт = общая клетка декартова произведения делений. Для группы без подгрупп —
одна клетка, ограничения совпадают с обычными.

**Индикаторы мягких критериев — нижние оценки.** Например, окно `gap ≥ pre + suf − y − 1`: при
минимизации CP-SAT сам доводит индикатор до точного значения, а лишних ограничений вдвое меньше.
Точные определения (`y ≤ Σ o`) стоят только там, где у критерия бывают **бонусы** (предпочтения
«+1/+2»): иначе решатель «нарисовал бы» занятость ради бонуса. Поэтому разбивку штрафа для
диспетчера всегда считает валидатор, а не модель; тест сверяет их на задаче, решённой до оптимума.

**Агрегированные аудитории.** Для каждого типа достаточно условия Холла по порогам вместимости:
множества «аудитории вместимостью ≥ c» вложены, и для вложенных множеств условие Холла
необходимое и достаточное. Конкретные номера — потом, точным и быстрым алгоритмом.

**Склейка мигающих пар на этапе 2.** Если в каждой неделе условие Холла выполнено, то после
сортировки и попарной склейки нечётных/чётных мигающих в «сущности» размера max(a, b) оно
выполнено и для сущностей вместе с еженедельными — значит, этап 2 всегда находит назначение.

**Фаза 0 и полная подсказка.** CP-SAT ищет первое решение без целевой функции на порядок быстрее.
Найденное решение целиком (включая индикаторы) передаётся подсказкой — оптимизация стартует с
допустимой точки.

**Схема «через неделю» — те же переменные мигающих пар.** Элемент с n парами получает только
переменные `b[u,s,k]`; выбор недели — две булевы `z_k` с `Σ z = активность единицы` и
`Σ_s b[u,s,k] = n·z_k`; «по две подряд» — каждое вхождение не больше суммы соседних в тот же день
той же недели. Отдельного типа переменных не понадобилось, поэтому агрегированные аудитории,
клетки групп и этап 2 работают без изменений.

**Дистант с бронью — признак, а не формат.** Формат описывает студентов: для них это онлайн, и
правила смены формата в день применяются как есть. Аудитория при этом нужна (1 место): единица
получает потребность в аудитории, и преподаватель считается «на площадке» для критерия «не
приезжать ради одной пары».

**Аудитории — множества подходящих, условие Холла и отсечения (0.4.0).** У каждого занятия —
множество подходящих аудиторий R (тип, вместимость, оборудование занятия и преподавателей, без слотов
«занята не нами»). В каждом (слот, неделя) для наборов S из семейства {все различные R, их попарные
объединения, общее объединение, найденные отсечения}: занятий с R ⊆ S не больше |S|. Для вложенных
множеств это и есть условие Холла — точное. Если этап 2 всё же не находит назначения, он сообщает
узкий набор N(U′) (из алгоритма Куна: занятия U′, которым вместе доступно меньше |U′| аудиторий) —
набор добавляется в семейство во всех слотах, модель решается снова. Редкий второй случай —
«по неделям хватает, но еженедельное занятие не может занять одну аудиторию обе недели» — запрещается
конкретное сочетание занятий в этом слоте.

**Модель заново для каждого варианта.** В OR-Tools 9.15 ограничение нельзя удалить, а уровни
лексикографии одного варианта не должны ограничивать следующий. Построение модели — ~1 с,
на фоне минут поиска это незаметно.

**Валидатор внутри решателя.** Каждый вариант проверяется независимым кодом до выдачи. Если
модель CP-SAT и валидатор расходятся — это баг, и он должен упасть громко.

## Веб-слой (этап 4)

```
 PostgreSQL / SQLite ── timetable.models ──► services.problem.build_problem() ──► domain.Problem ──► ядро
                                ▲                                                          │
                                └── services.variants.save_variant() ◄── Schedule + отчёт ◄┘
                                        (снимок Problem в JSONB + назначения)
```

* Ядро не знает о Django. Весь перевод «строки БД ↔ dataclass'ы» — в `timetable/services/problem.py`;
  идентификаторы задачи — первичные ключи БД строкой (тип аудитории — код).
* Вариант хранит снимок задачи: штрафы и проверка валидатором воспроизводимы, даже если
  справочники потом поправили или элемент нагрузки удалили (`item_key` вместо обязательного FK).
* `build_problem` делает постоянное число запросов (prefetch), поэтому время сборки не растёт с
  числом элементов нагрузки (≈0,06 с на 328 элементах).
* Импорт xlsx идёт в одной транзакции и откатывается при любой ошибке или в пробном режиме —
  в БД не бывает «половины файла».

## Производительность

Ориентиры на синтетике масштаба §1 (25 групп, 45 преподавателей, 25 аудиторий, ~330 элементов
нагрузки; модель ~27 тыс. переменных и ~64 тыс. ограничений):

* построение модели — ~1 с;
* первое допустимое решение — ~2 с (фаза 0);
* качество растёт ещё минуты: на 2 ядрах штраф за 40 с ~12 000, за 120 с ~5 000
  (посаженное случайное решение — ~28 000). На целевом сервере (8 ядер) — заметно быстрее,
  `bench` покажет точные цифры на вашем железе.

Бутылочные горлышки: окна у групп/преподавателей (много индикаторов) и предпочтения курсов
(конкурируют с жёсткой теснотой). Если не хватает качества — сначала увеличивать время и ядра,
затем рассмотреть LNS-эвристику поверх CP-SAT (интерфейс `Solver` это позволяет).
